## Design decision record (2026-07-13)

The original backlog (IT-045/046/047, dated April) predates the trust-model discussion. Three refinements, each with its rationale in `InnerTable-Trust-Model-Rationale.md`:

**1. Categories are a small, seeded factor set — separate from v0.4.0 `place_tags`.**
Categories are the interpretable *factors* the trust model is keyed on (`(user, user, category)`); a fixed shared set is what makes those comparisons valid graph-wide (Barra, not PCA). `place_tags` stay what they are — freeform, read-all *place classification / candor*. Different jobs, different audiences; not merged. **Keep the factor set small** (Peter's limited-global-factors-vs-spurious-full-covariance point). We still seed from the existing cuisine dropdown for continuity, but the *tuning surface* shows only the user's most-used categories by default (IT-047 already does this), and the set is pruned over time via the anchor-calibration loop (IT-111, v0.6). Resist proliferation.

**2. An override is a single nullable trust *weight*, not a signed `similarity_score`.**
This supersedes IT-046's `similarity_score(-1..1)` + `weight`. That design conflated the explicit signal with the thing v0.6 computes implicitly. Trust ≠ similarity: the explicit weight is *my judgment of a friend's authority* on a category (which can diverge from how much we agree), and v0.6 *blends* it with implicit Pearson similarity precisely because they're complementary. So we store one column:
`weight smallint CHECK (weight BETWEEN 0 AND 5)`, **NULL allowed**. NULL = "no opinion / use default" (≠ zero — same null≠low lesson as v0.4.0 notes). `0` = explicit mute. Raw ordinal, not pre-normalized (normalization is a v0.6 blending choice). Directional.

**3. Schema-forward for v0.6, no math now.**
v0.5.0 collects the explicit signal and nothing else. The forward-compatibility contract (how the weight feeds v0.6's `blended_trust = combine(explicit_weight, pair_similarity)`) is documented in the rationale doc §1.3. No similarity computation, no blend, ships here.

> **Concept — why `place_categories` isn't on the v0.5.0 critical path.** IT-045 also specs a `place_categories` join (which places are "seafood"). v0.5.0 trust is *explicit* — the user directly names the friend and the category — so nothing is computed *over places* yet. The place↔category join is only needed when v0.6 starts computing similarity from ratings. We still create it here (cheap, and it's real infra), with a best-effort backfill, but it is not what makes v0.5.0 work, and a thin/imperfect backfill does not block the release.

## Data model

### categories (seeded, controlled)

```sql
CREATE TABLE public.categories (
  id            uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  slug          text UNIQUE NOT NULL,          -- normalized, e.g. 'chinese','cocktail-bar'
  display_name  text NOT NULL,
  category_type text NOT NULL CHECK (category_type IN ('cuisine','venue_type')),  -- room for 'experience' later
  sort_order    int  NOT NULL DEFAULT 0,
  created_at    timestamptz NOT NULL DEFAULT now()
);
```

Seed from the current `index.html` `f-cuisine` dropdown for continuity (American, Italian, Mexican, Japanese, Chinese, Thai, Indian, Mediterranean, French, Korean, Vietnamese, Middle Eastern, Seafood, Brunch, Pizza, Cocktail Bar, Wine Bar, Craft Beer, Other), typed cuisine vs venue_type. RLS: **read-all** (categories are shared reference data, not candor), **no client writes** (seed/curation only — insert via migration).

> The seed is ~19 for continuity, larger than the ~8–15 "keep it small" target. That tension is resolved at the *surface*, not the table: the tuning grid shows a personalized short list by default with a "show all" expander, and the anchor loop (IT-111) prunes the true factor set later. Documented so a future session doesn't "fix" the seed prematurely.

### place_categories (join — v0.6 prep, not v0.5.0-critical)

```sql
CREATE TABLE public.place_categories (
  place_id    uuid NOT NULL REFERENCES public.places (id) ON DELETE CASCADE,
  category_id uuid NOT NULL REFERENCES public.categories (id) ON DELETE CASCADE,
  created_at  timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (place_id, category_id)
);
CREATE INDEX ON public.place_categories (category_id);
```

Backfill best-effort from each place's existing free-text cuisine (map string → category slug; unmapped rows just don't get a join row). RLS: read-all, no client writes in v0.5.0 (place→category editing UI is deferred). Existing free-text cuisine and `place_type` **stay as fallback** (same pattern as v0.4.0 keeping `place_type` behind tags); dropping them is later cleanup.

### friend_taste_overrides (the explicit weight)

```sql
CREATE TABLE public.friend_taste_overrides (
  rater_id    uuid NOT NULL REFERENCES public.users (id) ON DELETE CASCADE,  -- me
  friend_id   uuid NOT NULL REFERENCES public.users (id) ON DELETE CASCADE,  -- them
  category_id uuid NOT NULL REFERENCES public.categories (id) ON DELETE CASCADE,
  weight      smallint CHECK (weight BETWEEN 0 AND 5),   -- NULL = no opinion/default; 0 = mute; 1..5 = ascending trust
  updated_at  timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (rater_id, friend_id, category_id),
  CHECK (rater_id <> friend_id)
);
```

**RLS (no SECURITY DEFINER needed — unlike friendships, you only ever write your own `rater_id` row):**

```sql
ALTER TABLE public.friend_taste_overrides ENABLE ROW LEVEL SECURITY;
CREATE POLICY "own overrides: select" ON public.friend_taste_overrides
  FOR SELECT TO authenticated USING (rater_id = auth.uid());
CREATE POLICY "own overrides: insert" ON public.friend_taste_overrides
  FOR INSERT TO authenticated WITH CHECK (rater_id = auth.uid());
CREATE POLICY "own overrides: update" ON public.friend_taste_overrides
  FOR UPDATE TO authenticated USING (rater_id = auth.uid()) WITH CHECK (rater_id = auth.uid());
CREATE POLICY "own overrides: delete" ON public.friend_taste_overrides
  FOR DELETE TO authenticated USING (rater_id = auth.uid());
```

**Optional integrity guard:** RLS lets me insert an override for a *stranger* (harmless — I just can't see their entries — and pre-populates if we later friend). If we want to forbid it, a `BEFORE INSERT/UPDATE` trigger calling the existing `is_accepted_friend(rater_id, friend_id)` helper rejects non-friends. Recommend **deferring the guard** for alpha (keep it simple); note it as the clean fix if stray rows bother us.

## Phase 3 — Taste service layer + casual 5-dot grid (IT-047)

**New file:** `src/js/taste-service.js` — `getCategories()`, `getMyOverrides()`, `upsertOverride(friendId, categoryId, weight|null)`, `getMostUsedCategories()` (personalize columns from the user's own entries). Reuses `friends-service.js` `getMyFriends()` (accepted only) for grid rows.
**Touches:** `index.html`, `src/js/app.js` (view switching, existing pattern), `src/js/ui-render.js`, `src/styles/main.css`.

1. **"Rate my friends' taste"** surface: accepted friends as rows, the user's most-used categories as columns; each cell a **5-dot** control (1–5 = ascending trust). Unset cell = default (renders empty); casual mode does **not** expose `0`/mute (avoids the "no dots vs zero dots" ambiguity — mute lives in quant mode, Phase 4).
2. **"Show all categories"** expander → full seed list as columns.
3. **Save-as-you-go:** debounced (~300 ms) upsert; clearing a cell deletes the row (back to NULL/default), it does not write 0.
4. **Explicit refresh after own writes** (IT-107 lesson — realtime is for *other* users' changes; not needed here since overrides are private to the rater).

**Acceptance check:** grid renders for all accepted friends × most-used categories; tapping dots persists; "show all" expands; cleared cells become NULL (not 0) in the DB; reload shows saved state.
